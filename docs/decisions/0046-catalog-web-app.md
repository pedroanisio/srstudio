# ADR 0046: The catalog is a small web app, not one file

- Status: proposed; implemented 2026-10-30 on `feat/catalog-site` (`srstudio.catalog_page`, `srstudio.catalog_data`,
  `srstudio.catalog_server`, `srstudio/assets/catalog/`, `srstudio page --site`, `srstudio serve`;
  `tests/test_catalog_page.py`, `tests/test_catalog_data.py`, `tests/test_catalog_server.py`,
  `tests/test_catalog_app.py`)
- Deciders: the operator (pedroanisio), implementation drafted by Claude Opus 5.5 in Claude Code
- Back to the [library README](../../README.md)

## Context

The catalog was one self-contained HTML file with every video and image embedded as a data URI, so that it opened
offline. It reached 125.5 MB: 105.6 MB of base64 video, 15.7 MB of JPEG, 1.5 MB of MP3, 1.0 MB of fonts and 0.5 MB of
PNG across 461 data URIs. The operator's browser no longer renders it. Everything else in the page is small, so the
root cause is the embedding and no amount of compression removes it: each new episode adds to a file the browser
must parse whole before it shows anything.

A folder of files fixes the weight, but one long page of 104 players still fetches a poster for each one when it
loads, whatever `preload` says, and it can only be read top to bottom. The catalog has grown past that: 242 parts, 111
video entries and 9 styles, and the operator needs to go from a character to its videos and back.

## Decision

1. **`srstudio page --site DIR` writes a folder**, `index.html`, `catalog.json` and `media/<content-hash>.<ext>`,
   with relative URLs. `--site` replaces `--out`: the single-file mode is removed, because a mode that writes a page browsers cannot
   open is not an option worth keeping.
2. **No data URI remains**, including the 8 inside the frozen base page (2 fonts, 6 sounds), which become media
   files. A URL in CSS or in a script's string resolves against the document, so the text around them does not
   change. The build refuses a page that still holds one, in any encoding, and a page past `INDEX_LIMIT`.
3. **Names follow content.** A rebuild writes only what changed. Files are hard-linked from the cache, so the site
   costs no second copy of the videos; they are copied across devices, and when a link would have to change the
   mode of the cached file.
4. **A failed build leaves the previous site working.** Media are placed first, each through a temporary name, then
   `catalog.json`; `index.html` is replaced last, atomically; files nothing references are removed only after that.
5. **`srstudio serve SITE`** is `ThreadingHTTPServer` with a handler of our own. It is read-only (GET and HEAD), serves
   only inside the folder, lists nothing, and answers ranges with 206 and `Content-Range`, or 416. Media are cached
   as immutable; everything else is revalidated. The default bind is loopback because there is no authentication.
6. **`index.html` is a shell and `catalog.json` is the content.** The shell is the frozen base page with a navigation
   bar: its sections become the home, *Pacotes* and *Motor* views, and its script runs once, the first time one of
   those routes opens. Everything else is drawn in the browser by `assets/catalog/app.js`, plain JavaScript with no
   framework and no build step, published with its stylesheet as content-addressed media. Only the current view has `<img>` and `<video>` elements, so
   only its media load.
7. **Each item has a hash route**, such as `#/personagens/rosa`, `#/estilos/toon`, `#/videos/camera-off` and
   `#/videos?estilo=toon`. Back, forward and shared links work with no server routing, and a search is a route too.
8. **`catalog.json` is generated by the build and has a schema.** `srstudio.catalog_data` defines it as frozen
   dataclasses, versioned by `schema_version`; a reader rejects unknown fields and checks what types cannot express,
   such as references that do not resolve. Which videos use a part comes only from the measured `usage.json`. The
   build stops when the report names a part that is not registered, so stale usage is never shown as fact.
9. **What is missing is said.** A part with no still, a part measured unused, and an episode the report could not
   measure each carry a visible mark. The six packages are entries in *Vídeos* marked `pacote`, linking to their
   players; a measured project with no render is listed and says so.

## Rejected alternatives

- **Keeping one file, with lighter encodes.** Base64 adds a third to every byte, and the browser has to decode all of
  it before the first paint. Halving the video bitrate buys a few dozen more episodes and hurts the part of the page
  that matters. The catalog grows by a batch at a time, so the limit would come back.
- **Python's `http.server` (`SimpleHTTPRequestHandler`).** It has no Range support, so a browser cannot jump to a part
  of a video it has not downloaded, which is what clicking a line does. It also lists folders, follows symlinks out
  of the root and has no way to mark media as immutable. Fixing those is most of the handler we wrote.
- **A web framework (Flask, FastAPI, Starlette) or a static server dependency.** The server is a read-only file
  server for one person on loopback. `CLAUDE.md` adds a dependency only when it replaces code the project would
  otherwise write and maintain, and a framework replaces little here: the handler is under 200 lines of standard
  library, and the rules on traversal, symlinks and hidden files would still be ours. It would bring an install and
  an upgrade path to save a part of that.
- **Opening `index.html` from disk with no server.** The app fetches `catalog.json`, and browsers refuse `fetch` on a
  `file://` page, so the page would stay empty. Inlining the document in the page would allow it, but only by keeping
  the page itself as the one thing that grows; the document is already 0.4 MB.
- **One server-rendered page per item.** About 360 static pages, or a server that builds them, would give each item a
  real URL too. Static pages would repeat the navigation and the base page in each file and make every template
  change rewrite all of them, and a rendering server would turn a read-only file server into an application. Filters
  and the search would still need a document and a script in the browser. The one JSON document costs one fetch, and
  it is also what tests and other tools can read.
- **Path routes (`/personagens/rosa`) with the History API.** They look cleaner but need the server to answer every
  path with the shell, and the server would then answer 200 for a path that does not exist. Hash routes need nothing
  from the server, which stays a plain file server.
- **A frontend framework with a build step.** The views are string templates over one document, about 440 lines. A
  framework or a bundler would add a toolchain to a Python project to replace them, and a build the catalog service
  would have to run.
- **Writing the base page's sections into `catalog.json`.** The six packages' players, their inventories and the
  engine pages are frozen markup with their own script. Keeping them as hidden sections of the shell leaves that page
  unchanged and reachable, and its script waits until a route needs it.

## Consequences

- The catalog needs a running server. `tools/systemd/srstudio-catalog-web.service` keeps one up; the operator installs
  it. The root `catalogo-scene-render.html` is no longer written and goes stale.
- A browser holding an old page can get a 404 for media a rebuild removed, until it reloads. The page is revalidated
  on every load, so a reload always fixes it.
- `catalog.json` and `index.html` are replaced one after the other, so a load in that instant can pair the old shell
  with the new document. The shell reports a major version it does not know instead of drawing it, and a reload
  fixes it.
- The catalog needs JavaScript. Without it the page says so and the base page's sections stay hidden.
- A cold *Vídeos* view still fetches the posters inside the browser's lazy-loading margin. That is the browser's
  choice and it is bounded by the view, not by the size of the catalog.
- `generated/catalog/site` must stay on the same device as the cache for the hard links to save space; otherwise it
  costs a copy and nothing else.

## Addendum, 2026-10-30: an application shell

The first version kept the old page's reading order: a banner, prose cards per style, then a row of numbers. It served
the files correctly but read as a long document with a menu on top, and the operator's review was "this is not looking
like a webapp" and "improve the data/information disposition". The shell now is a fixed sidebar with a count per
section, and the banner never shows.

- The home view is a dashboard: headline numbers, one table comparing the styles (each number links to that filtered
  index), the share of each kind of part in use, and what is pending.
- Every index has one toolbar: style filter with counts, sort, use, grid or list. All of it lives in the route, so a
  view is a link, as the style filter already was.
- Details share one layout: path, title, content, and a data sheet. A style opens in tabs instead of one long page.

Rejected: a client framework, because hash routes over `catalog.json` already give every view, and ADR 0046's reason
for plain JavaScript stands; and removing the banner from the base page, because its numbers still feed the dashboard's
specifications and the base stays the one source for the packages. The home view now loads one poster per style,
bounded by the number of styles, where it used to load no image.
